#### THE FIVE THINGS THAT WOULD HAVE BEEN WRONG

Each of these is a plausible transcription that passes a self-round-trip and
fails against vanilla.

1. **`Crypt.digestData` hashes its arguments in a different order from its own
   parameter list** — `(serverId, PublicKey, SecretKey)` hashes serverId, then
   the **secret**, then the key. And the hash is
   `new BigInteger(digest).toString(16)`: signed two's-complement with leading
   zeros stripped, so server id `notch` gives a hash beginning `-` and server
   id `-` gives a **38-character** one.
2. **`ClientboundSetPlayerTeamPacket.Parameters` puts `options` LAST** in 26.2,
   with the colour an `Optional<TeamColor>` and both rule enums varints. A body
   in the older documented order is the same length for an uncoloured team, so
   it decodes without error with the flags in the visibility field.
3. **`PortalShape` never reads the frame's corners.** A frame missing all four
   is a valid portal; a perimeter scan refuses it.
4. **Six of `MerchantOffer`'s ten fields are `writeInt`**, fixed 32-bit
   big-endian, on a wire where nearly every other integer is a varint — and the
   packet's own `containerId` and `villagerXp` *are* varints, so one packet
   mixes both.
5. **`PortalProcessor` is `portalTime++ >= transitionTime`** — a post-increment,
   so a delay of 80 fires on the 81st tick — and `decayTick` subtracts **four**,
   so one tick outside costs four inside.

#### THE BRIEF WAS WRONG ABOUT TWO THINGS AND BOTH ARE LARGE

* **Villager trades are datapack data in 26.2, not `ItemListing` lambdas.**
  `VillagerTrades` is a list of `ResourceKey<VillagerTrade>` constants and
  nothing else; the trades are 388 JSON files, the pools 73 tags and the
  amounts 68 `trade_set` entries. There is no RNG to seed, no lambda to
  instantiate and no JVM involved: `ci/dump-villager-trades.sh` reads the
  extract. The brief's "a Golden can instantiate them with a seeded
  RandomSource" describes a previous version.
* **`EncryptionConfig` does not exist in this jar.** `unzip -l` finds no such
  class. Encryption is set up by two `Crypt.getCipher` calls in `handleKey`.

#### A GOLDENGEN TRAP FOUND THREE TIMES — WRITE THIS ONE DOWN

**`Bootstrap.bootStrap()` is not a loaded server.** It registers things and
freezes the registries, and it leaves two kinds of derived state unbound:

* **block and item TAGS.** `BlockState.is(BlockTags.FIRE)` is false for
  `minecraft:fire` inside a bare goldengen JVM, so `PortalShape.isEmpty`
  answered differently from a real server and the first `ci/portal-golden.sh`
  run captured `fire-inside-2x3` as a 0x0 non-portal. `bindTags` throws
  "Registry is already frozen"; the fix is
  `prepareTagReload(new TagLoader.LoadResult<>(...)).apply()`.
* **item DATA COMPONENTS.** `new ItemStack(Items.EMERALD)` throws
  `NullPointerException: Components not bound yet`. The fix is
  `BuiltInRegistries.DATA_COMPONENT_INITIALIZERS.build(VanillaRegistries.createLookup())
  .forEach(PendingComponents::apply)`.

And a third, different in kind: `RegistryAccess.EMPTY` has no `minecraft:item`,
so `ItemStack.STREAM_CODEC` throws "Missing registry" — a merchant capture
needs `RegistryAccess.fromRegistryOfRegistries(BuiltInRegistries.REGISTRY)`.
(`EntityMoveGolden` warns against that spelling; its caveat is about building a
`Level`, which needs datapack registries, and does not apply to an encoder.)

**Both tag and component cases were caught by a guard, not by inspection.** Any
future goldengen program that touches a tag or an item has one of these.

#### A DEFECT IN THIS PROJECT'S TOOLING, NOT IN VANILLA

**`serde_json` without its `float_roundtrip` feature parses a
17-significant-digit double one ULP wrong.** Measured on
`world_border.json`: the text `14.600000000000001` (bits
`4624408687374709556`) comes back from `as_f64()` as `14.6` (`…555`). Writing
more digits cannot fix it, which is why this area's goldens carry
`<field>Bits` and never compare the decimal.

**The sweep it demanded came back clean, and that corrects the first reading
rather than confirming it.** `crates/rustmc-data/tests/golden_float_precision.rs`
walks every committed `golden/` fixture and parses every decimal both ways:
**61 files, 843 decimal literals, 5 files carrying 38 doubles serde_json
cannot read back** — and *no reader in this workspace parses any of the 38*.
The project had already converged on carrying the bits, independently, in
three spellings: `golden_rng.rs:135` "Compare IEEE-754 bits, never the decimal
repr", `golden_noise.rs:5` "Everything is compared as raw IEEE-754 bits",
`attributes.rs:44` "the bits are what is read". So the alarming version of
this finding — "26 `as_f64()` sites, any could be silently wrong" — overstated
the live exposure. What is left is a ratchet that reddens on the commit that
adds the next misreadable golden, plus a second test asserting the two parsers
still disagree, so a fixed serde_json retires the guard loudly.

#### WHAT IS REFUSED, AND WHY — SO NOBODY RE-RUNS IT

* **`MinecraftSessionService.hasJoinedServer`.** A live HTTPS call to Mojang
  whose answer depends on a third party's database. No recording can stand in
  for it and no golden can be taken. `online.rs` returns an error naming
  itself, and `tests/online_login.rs::the_refusals_are_refusals` **asserts it
  stays a refusal**, so a stub appearing later reddens a test rather than
  silently admitting anyone who completes a handshake against a published key.
* **RSA key generation.** Unlike the lookup this one *is* verifiable without an
  oracle (`n == p*q`, Miller-Rabin, `e*d ≡ 1`). Absent because it needs a
  CSPRNG and because with the lookup refused a generated key has nowhere to go.
  Also asserted to stay absent.
* **`VillagerTrade.getOffer`.** Applies loot functions (41 of 388 trades) and a
  loot predicate (27). Both are the loot layer's; `deal_offers` takes the offer
  decision as a callback rather than guessing.
* **An `ItemCost` or result carrying components.** One trade's `wants` has a
  component predicate and 41 results take modifiers. `merchant::write` returns
  an error rather than dropping them.
* **The gameplay oracle.** The brief names it as the instrument for anything
  wire-visible, and no scenario was added. A border-set scenario needs the
  server to implement `/worldborder`, a scoreboard one needs `/scoreboard`, and
  the command surface is another lane's files. Writing the commands to make a
  scenario possible would have put this branch in the middle of that lane's
  tree. **This is the one part of the brief not attempted**, and it is a
  sequencing call rather than a judgement that it cannot be done.

#### WHAT IS TRANSCRIBED BUT HAS NO VANILLA ORACLE — SAID PLAINLY

Two things. Their tests say so in their own headers rather than letting a green
result imply parity.

* **`AbstractVillager.addOffersFromItemListings` and its `WithoutDuplicates`
  sibling.** Running vanilla's version needs a `LootContext`, which needs a
  `ServerLevel`. The draw sequence is pinned against a scripted RNG, which
  catches a change and does not prove parity.
* **`PortalProcessor`.** Same reason — a `ServerLevel` and an `Entity`.

#### ONE THING THAT WILL BITE THE NEXT AGENT IN THIS REMOTE DIR

**Do not run the `docs/AGENT-BRIEF.md` inner-loop rsync while a gate is running
in the same `RUSTMC_REMOTE_DIR`.** `worldsys-t0c` came back
`T0 RED — ci/entity-id-allocator-falsify.sh: an injected fault went unrefused`
on the arm `counter retyped to AtomicI64`. That falsifier `sed`s
`crates/rustmc-server/src/entities.rs` in place and restores it after; a
concurrent `rsync --delete` put the unpatched file back before the check read
it, so the injection was not there to be caught. The same tree was **T0 GREEN**
two commits earlier and this branch touches nothing in that file.

`ci/gate-lock.sh` is the mtime mutex for precisely this and a hand-rolled rsync
takes none of it. The failure mode is the worst available shape: a *falsifier*
reporting that an injection went unrefused, which reads as a defect in whatever
branch happens to be under test.
