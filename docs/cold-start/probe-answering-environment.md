# Cold start — branch `probe-answering-environment`

### COLD START — branch `probe-answering-environment` off `f2641a6` (`tables-refusal-ledger`, 24 commits), 2026-08-18

What to run, and in what order.

```text
ci/use-golden.sh                regenerate use_without_item.json  (~25 s, jar)
ci/placed-golden.sh             regenerate set_placed_by.json     (~35 s, jar)
ci/probe-absences.py            every rule the jar declares that a table has no row for
ci/probe-absences.py --check    refuse if an absence is unexplained, stale or miscited
ci/probe-absences-falsify.py    arms on shadow trees (T0, needs the jar)
ci/refusal-ledger.py --check    refuse if a refusal population moved
```

Both generators write into `data/vanilla/`, which is **gitignored and
generated**. The copy on disk in a fresh worktree is whatever the last run in
that tree produced and can be a week old — this branch found the checked-in
tree's `use_without_item.json` still carrying the 39 `Components not bound yet`
refusals that were closed on 2026-08-12. Regenerate before you measure, and
never read `~/rustmc/data/vanilla/` for a number about *your* tree.

Two things cost half an hour between them and neither is in any other file:

* **`ci/gen-gameplay-tables.sh` needs `cargo` on `PATH`.** It dies at
  `ci/dump-recipe-unlocks.sh` with `cargo: command not found` after twelve
  generators have already run, which looks like a generator defect and is a
  login shell that has no `$HOME/.cargo/bin`. `export
  PATH=$HOME/.cargo/bin:$PATH` first. `docs/cold-start/ci-probe-stances.md`
  found the same thing in August and it is still true.
* **A gate directory needs its own tables, not a symlink to yours.**
  `ci/t0-remote.sh` excludes `data/vanilla` from the rsync deliberately, so a
  fresh `~/rustmc-<lane>` has none. Symlinking the worktree's in is the obvious
  move and `ci/check-use-probe-falsify.sh`'s `real-table` arm refuses it —
  `FOREIGN — generated in /home/sayer/grit/work-probe, not in
  /home/sayer/rustmc-probe2` — which is the arm working, because a table
  generated by another tree's dumper says nothing about this one's. Run
  `ci/gen-gameplay-tables.sh` **in the gate directory**, or gate in the
  worktree if you are already on the box.

## The one-paragraph version

`UseGolden.TableLevel` answered `Blocks.AIR` for a position it was not given and
`null` for a block entity, so a rule that read either took the empty branch and
the probe emitted **no row rather than a refusal**. Silence, not debt — and a
refusal is counted while an absence is not. 22 overrides had no row across 102
registry blocks, 100 of them the probe's environment. The level answers now.
`ci/probe-absences.py` derives its trigger from the jar and never from the
table: **3 overrides with no row** over 3 registry blocks, 0 of them the
environment. (This branch left it at 4 / 6 / 3. The last `environment` entry
was `CommandBlock`, and `docs/cold-start/server-level-gate.md` closed it by
putting the gate in the row rather than by porting the rule.) `use_without_item.json` went 184 rows to 274 and
`set_placed_by.json` 50 to 56, and neither lost a row.

## The four mechanisms, because only the first was foreseen

The estimate this branch inherited was "a block entity in the harness, one
line". The block entity closed twelve of the thirteen silent `useWithoutItem`
classes and none of the largest.

**1. A real block entity, supplied and not refused.**
`EntityBlock.newBlockEntity(pos, state)` is what vanilla's own `LevelChunk`
calls. Four cases, one of which throws: held and declaring one → the real
`BlockEntity`; held and declaring none → `null`, which is vanilla's own answer;
not held → `null`, flagged on the row; declaring one and building `null` →
**refusal**. The last is `MovingPistonBlock` alone in the whole registry.

**2. Vanilla's own alarm, un-muted.** `SignBlock.useWithoutItem` gets past its
block-entity gate and then hits `if (!(level instanceof ServerLevel)) {
Util.pauseInIde(...); return CONSUME; }`. `TableLevel` is not a `ServerLevel`
and cannot be. `pauseInIde` does nothing because `SharedConstants
.IS_RUNNING_IN_IDE` is false — and that field is `public static boolean`, **not
final**, beside a public `Util.setPause(Consumer<String>)`. Arming both turns
the message into the refusal: 1,344 cells over 48 blocks, all signs.

**Two traps in that, both hit.** `pauseInIde` logs the exception with a stack
trace *before* it reaches the pauser, log4j's console appender writes to the
same stdout the JSON goes to, and the first armed run produced a file whose
first byte was `[`. One logger is silenced (`net.minecraft.util.Util`) and not
the root. And the flag and the pauser are independent switches, either of which
left off makes the whole mechanism a silent no-op, so the dumper raises the
alarm against itself at startup and throws if nothing comes back.

**3. Two player stances.** `CakeBlock.eat` opens `if (!player.canEat(false))
return PASS`; `canEat(false)` is `abilities.invulnerable || foodData
.needsFood()`. `HarnessPlayer.gameMode()` answers `CREATIVE` and a real creative
player has `invulnerable = true`. This one never has. `STANCES[0]` is not free
to change, so `hungry` and `invulnerable` measure the gap rather than repairing
it out of sight — 18 blocks, one cake and seventeen candle cakes.

**4. A face that is not `UP`.** Every recorded cell is the `FACES[0]` probe.
`BellBlock.isProperHit` rejects `UP` and `DOWN` outright and
`ChiseledBookShelfBlock.getHitSlot` answers empty for any face that is not
`FACING`, so both were uninteresting under the recorded face and had no row —
while `faceSensitive` had been `true` for both all along and nothing read it at
emit.

## The column that replaced the silence, and why it is not a throw

`reads` is a closed vocabulary — `air-world`, `no-entities`, `no-block-entity` —
and `interesting()` emits any cell that carries one. It says the thing neither a
refusal nor a plain row could: *measured, and the answer turns on something this
world has none of.*

**Do not "fix" it into a throw without re-running the measurement.** Making
`getBlockState` throw for an unheld position — the `ShapeGolden` discipline —
moves 1,416 cells of `use_without_item.json` from a row to a refusal across
`NoteBlock`, `BedBlock`, `RedStoneWireBlock` and `ComparatorBlock`, and reveals
**no block that was not already in the table**. In `set_placed_by.json` the same
read is the only thing separating `minecraft:repeater`, `minecraft:comparator`
and `minecraft:pale_moss_carpet` from a block with no rule. One table wants a
throw and the other wants an answer; the column serves both.

`ci/probe-absences.py`'s structural claim has three states now — immune,
exposed, flagging — and asserts the third by **counting the ways out** of
`getBlockState`, `getBlockEntity` and `Probe.interesting()`, so that a change
leaving `readUnheldPosition = true` in place and inserting `if (true) return
AIR;` above it cannot pass. `interesting()` is in the claim because a flag
nothing emits is exactly the `blockEntityAsked` field that sat unread for four
months.

## The other half of the right-click

`use_item_on.json` is the optional fifth population and nothing under `crates/`
opens it, so most trees never build it. Build it once here, because it is where
this branch's change is largest and where the argument for making it came from:
its dumper **refused** on the block-entity ask where `UseGolden` answered
`null`, so the two halves of one right-click gave 2,593 loud refusals against 90
silent absences.

Both are closed by the same change, because neither refusing nor answering
`null` was the answer.

```text
  block-entity refusals   2,593 -> 0
  states refused outright        64, all `recipeAccess`
  states refused in part         25, `getChunkSource`
  states recorded             4,319 of 4,537
  (state, item) cells        44,078
```

`ci/use-item-on-golden.sh` takes about 25 minutes now — it ran in ~95 s while
every block-entity rule bailed at the ask, and the rules run to the end now.
Budget for it, and expect `ci/check-use-probe.py` to refuse the first write:
`SignBlock.useItemOn` reaches `player.mayBuild()` once it has a block entity, so
48 signs become probe-dependent and want entries. 25 probe-dependent blocks
become 73, which is what a refusal costs a sweep and is invisible from inside
the refusal.

## Three things that will trip you

**1. The inherited "ten rows" is fifteen.** `TableLevel`'s comment said "ten of
its rows have recorded the null branch since the table was created" and
`PARITY-ROADMAP` §71.4 costed the repair on it. Flagging the ask per cell and
intersecting with the table as it stood gives **210 cells over 15 blocks**.
Nothing in the tree had ever derived ten.

What they say now, measured against the table as it stood: **eleven gain
`opens: menu`** (dispenser, dropper, hopper, furnace, smoker, blast furnace,
brewing stand, enchanting table, beacon, crafter, and the lectern on its 8
`has_book=true` cells only), **three gain `reads: ["air-world"]`** (note block,
comparator, ender chest), and **`moving_piston` becomes 12 refusals**. None lose
a cell. §80.3 has the table.

**2. `opens` exists because `Player`'s screen methods are empty bodies.**
`openMenu`, `openTextEdit`, `openCommandBlock`, `openStructureBlock`,
`openJigsawBlock`, `openTestBlock`, `openTestInstanceBlock`, `openDialog` and
`openItemGui` are all `{}` on `Player` and all overridden on `ServerPlayer`. So
every container in the game recorded `consumes: true, writes: []`, which reads
as "the click was eaten and nothing happened". `ci/probe-reads.py` had already
written down that the `OptionalInt` "is dropped on the floor by every caller in
the jar" — the return could never have carried it and the call had to.

**3. A `probeOnly` or `faceOnly` row carries no cells, and that is the point.**
It says "this block has a use rule and the base probe cannot see it", which is
strictly more than nothing and strictly less than a port. `crate::useblock`
skips any cell that is not `consumes: true`, so the table grew by 90 rows and
the module's behaviour did not change at all.

## And the next silence, which is bigger than what is left of this one

`ci/probe-absences.py` prints it beside the absences now. **8 probe rules gate
on `instanceof ServerLevel` over 82 registry blocks, 7 of them in silence, over
34 registry blocks, and only one of the eight — `SignBlock` — announces
itself** through `Util.pauseInIde`, which is the only reason this branch could
refuse anything on it.

```text
  announces  SignBlock.useWithoutItem
  silent     BarrelBlock, ChestBlock, EnderChestBlock, RespawnAnchorBlock,
             ShulkerBoxBlock, SweetBerryBushBlock  (useWithoutItem)
  silent     CommandBlock (setPlacedBy)
```

`TableLevel` is not a `ServerLevel` and cannot be, so those rows are decided by
what the harness is. `minecraft:ender_chest` is the case to read first: it is
one of the fifteen rows this branch changed, it gained `reads: ["air-world"]`
for the `isRedstoneConductor` check above it, and it did **not** gain `opens`,
because `openMenu` is inside the gate. Its row still says `consumes: true,
writes: []` and is right by the same coincidence the signs were right by.

`ci/probe-absences.py` costs about 12 s and 4 s of that is the disassembly.
**Do not filter the class list by whether the bytes mention `ServerLevel`** —
it is sound in that direction and it does not pay: reading ~70 class entries out
of the zip costs what `javap` saves (24.8 s per-class-open, 12.5 s one-pass,
12.1 s no filter). Built, measured, deleted.

**Reported rather than refused, deliberately.** Six of the eight have rows, and
refusing them all deletes every chest, barrel and shulker box row over a branch
this project may never be able to take. Whoever prices the next harness should
price it off this number rather than off a hunch.

Two verdicts moved from `environment` to `out-of-scope` and **each moved on a
measurement, not a re-reading** — that distinction is written into the ledger's
header because `out-of-scope` is otherwise a place to file something
inconvenient. The structure block because it now runs to the end and what it
does has no column here; the jukebox because `PlacedGolden` now holds
`block.asItem().getDefaultInstance()` — what `BlockItem.place` holds, and what
`ItemStack.EMPTY` stood in for until `bindItemComponents` landed in the *other*
dumper on 2026-08-12 and nothing carried it across — and **the answer did not
change**, with zero other rows moving when the stack did.
